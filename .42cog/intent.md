# PilotDeck-RS：把 PilotDeck 后端从 TypeScript 重写为 Rust · 意向书

> 意向即行动。这一份文件决定这个系统会长成什么样。
> **只有一处必须你亲自过目：收敛方向。其余是草稿，看不顺眼再动。**
> 本文件写整体目标与完成边界；交付标准的细则见 [`specs/delivery/README.md`](../specs/delivery/README.md)，当前进度与下一步见 `state/takeover.md`。

## 收敛方向（唯一）

以 **`OpenBMB/PilotDeck@cc7c4e6`**（standalone_alpha1，2026-10-13）为固定基线，完成 **gateway、agent 循环 sidecar 和全部 CLI** 的 Rust 重写，使这三个入口在新实现上的对外行为与基线一致，TS gateway 退役；原版 `ui/server` 与前端不重写，但接到 Rust gateway 上必须照常可用。以**对着基线的行为验收、被替换实现的退役证据和真实使用验收**共同判定完成，具体是[交付标准](../specs/delivery/README.md)的八条。

**范围（2026-11-12 人定）。** 只做 gateway（原阶段 A）、sidecar（原阶段 C）、CLI（原阶段 D）。阶段 B（`ui/server` 的 Rust 重写）、前端重构、StaffDeck、各渠道的生产实现不做；渠道只要求启动表现与基线一致。此前按五个阶段分别计分的做法随之停用：三个入口用同一套标准验收，不再分阶段报分。

> 依据：2026-10-13 至 10-16 的原始方向见本文件的 git 历史与[边界决策](../docs/research/002_parity-boundary/decision.md)；2026-11-10 起本分支由一个会话直接负责；2026-11-12 人在会话里收窄范围（「阶段B和前端不用做」）、认可交付标准八条，并让主会话同步本文件。

## 真难题

一个 18 万行 vibe coding 的 agent 平台，**它的真实行为没有成文规格**——行为散落在 31 个模块的实现、9.8 万行测试和前端的隐含假设里。重写最难是**先把「什么叫一致」变成机器能判的东西**。尤其是在哪个颗粒度上保持一致，架构不合理怎么办，原始代码有错怎么办，测试或者探针本身有问题怎么办？

## 不做什么

| 不做 | 为什么不做 |
|---|---|
| 迁移期间不加新功能、不"顺手"改行为——**修 bug 除外**（2026-10-14 人定「默认修」） | 重写失控的第一原因。想到改进就记一条 issue，不当场做（demo-2/04 §六）。**什么算 bug（2026-10-14 人定）**：基线 ① 崩溃、挂起、丢数据 ② 与它自己的类型定义、文档或测试断言相矛盾 ③ 有安全问题。三条都不沾的是「行为偏好」，记 issue、不改。修了一律记进「已接受差异」清单（第 9 步建立），写明属于哪一条 |
| 不做阶段 B（`ui/server` 重写）、前端重构、桌面壳替换 | 2026-11-12 人定。原版 `ui/server` 与前端原样保留，只保证它们接 Rust gateway 的兼容性；不改基线的 `ui/` 与 `apps/desktop` |
| 不做 StaffDeck（SOP authority、审批、多用户隔离等）和各渠道的生产实现 | 2026-11-12 人定。渠道只做到与基线的启动表现一致（基线没装各渠道的 SDK，启用后只打一行然后照常启动） |
| 不移植按页渲染 PDF、写后语法诊断 | 前者依赖 mupdf，后者依赖 TypeScript 编译器等解析器出报错文案；对应的两个对拍场景保持不一致并留在结果里可见 |
| 不追上游最新提交 | 参照物在动，对拍就没有意义。升级基线 = 单独一条 issue，整批升 |
| 不照搬 TS 的模块内部结构（Bundle / 注入层层套）；**也不在移植一个模块的同时重构它** | 一致的是**协议和行为**，不是类图：模块边界与数据流照原样映射，内部按 Rust 习惯写。要重构放在移植前或移植后（`docs/research/001` 第二节第 1 条） |
| 不自己发明协议、字段、错误格式 | 以基线 TS 实测输出为准；有疑问跑一次基线看，不猜 |

## 真相源与权重

冲突时信谁，从高到低：

1. **基线 cc7c4e6 在对应入口实际跑出来的行为**（后端、CLI、UI 与桌面实测输出）
2. 基线对应范围的测试——测试与实测冲突时，以实测为准并记录
3. 基线的源码（`resources/PilotDeck/` 中对应范围，结论必须带文件行号）
4. 基线的文档（`docs/`、README）——可能过时，只作线索

上述排序用于确认原版事实；Rust 侧现有的代码、测试和夹具都排在这四者之后。**有意偏离基线的地方（只限基线自身的 bug）按登记的范围验收**：登记在对拍场景里，并在 `state/takeover.md` 留一行供人过目；仅有建议或记录不等于登记。冻结的判分文件（`specs/{parity,gateway-parity,ui-server-parity}` 下的）是上一轮流程的记录，不因改本文件而改动或放宽。

## 作品区

- 目录：`src/` 是产品实现区，一个 Cargo workspace，包含 CLI、gateway 与 sidecar 等 crate。
- 交付形态：三个 Rust 入口——`pilotdeck server`（gateway）、`pilotdeck` 的 CLI 子命令、独立可执行的 `pilotdeck-agent-loop-sidecar`（stdio 与 TCP 两种部署）。透明代理（Rust 转发给 TS 上游）只是迁移的中间状态，交付时不存在。
- 覆盖范围从基线枚举：gateway method 与参数、HTTP 路由、事件、落盘记录、配置键、环境变量、工具与参数、hooks、CLI 子命令等，清单在 `scripts/bbx/surface.json`，由 `node scripts/bbx/coverage.mjs --surface` 对照场景结果统计。[产品入口总账](../specs/product-coverage/README.md)是上一轮留下的记录，状态字段只当线索。覆盖完整不代表行为一致。

### 怎么算完成

验收手段是 `scripts/bbx` 的黑盒对拍（同一场景先后喂给基线和 Rust，比较 WS 帧、HTTP、CLI 输出、发给模型 provider 的请求、落盘文件）加四条构建测试命令。完成的判定是[交付标准](../specs/delivery/README.md)的八条同时满足，这里只列标题，门槛、允许不一致的清单和问题分级以那份文件为准：

1. **全量对拍稳定一致**：安静的机器上连续 3 轮结果完全相同，macOS 与 Linux 各一套；不一致的只能是明文清单上的项。
2. **表面覆盖完整**：清单里每个在范围内的项都被结果一致的场景碰到；不在范围的逐项列出理由，由人过目。
3. **盲审收敛**：连续两次只看基线、不看 Rust 实现的独立审查，都找不出安全与数据、主路径这两级的新差异。
4. **原版界面可用**：原版 `ui/server` 加前端接 Rust gateway，自动冒烟通过，人亲手用一次。
5. **构建与测试全绿、没有占位**：四条命令在 Linux 上全部通过；范围内没有 `todo!`、占位和转发给 TS 的兜底。
6. **TS gateway 退役**：透明代理已删除，有进程证据；独立的 sidecar 可执行文件保留。
7. **性能报告**：发布构建下对基线的启动耗时、每轮开销、内存、并发会话。
8. **真实使用**：人在最终组合上完成一组真实任务；主会话准备环境、步骤和证据，没做的如实记为待验。

对拍全绿或测试全绿本身不等于完成；任何一条没满足都不标完成。上一轮按阶段制定的规约（`specs/parity`、`specs/gateway-parity`、`specs/ui-server-parity`、`specs/cli-parity`）和计划（`docs/plan/001`–`006`）不再是验收依据：前三套的被测件是透明代理或一次性代理，证明不了 Rust 原生实现的行为。它们的冻结文件保留不动。
