## 3. 架构决定、工作包与首批派工

### 已确定的架构方向

- 保留纯 Agent 循环与 Gateway 实际能力之间的边界。
- 按项目及配置代际、会话、单轮执行整理资源所有权；会话缓存和历史状态不能每轮重建。
- 区分用户取消、正常轮次完成、会话关闭和进程停机。
- 默认 native 在进程内运行 Rust 循环；独立 sidecar 继续交付。
- 接通项目 `modules.agentLoop` 和环境部署配置，项目 binding 优先；主会话与子代理使用同一选择规则。
- stdio 管理子进程；TCP 管理连接和同实例恢复，不能通过重启新模块或重放副作用冒充恢复。
- 复用现有 `ExecutableTool`、`CustomRouter`、执行工厂及渠道接口；补公开注册、更新和释放机制。
- 原生扩展承诺 Rust 源码级集成，不增加动态库 ABI、WASM 或主进程 JS 引擎。
- 保留有证据支持的 `JsValue`／`JsString` 兼容语义，不以删除它们作为 Rust 化目标。
- 默认发行入口必须运行 native；旧透明代理退出正式业务运行链。

## 5. 里程碑、恢复入口与最终交付

### 里程碑

| 里程碑 | 关闭条件 |
|---|---|
| P0：可持续开发 | 正式工作区、cb8、有效并发额度、可信 bbx、公共接口和任务责任明确 |

性能从 P0 建立基线，在 P1 和 P3复测：核心与相同扩展集合分别比较安装体积、启动分布、全进程树空闲/负载内存，以及排除模型网络延迟后的执行开销。目标是缩小部署、降低内存并避免执行性能退化；未达目标的指标必须报告。
