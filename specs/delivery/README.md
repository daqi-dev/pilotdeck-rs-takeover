# 交付标准（gateway / sidecar / CLI）

> 2026-11-12 人在会话里认可：「这8条标准我认可，您写成正式文件吧」。
> 适用于接手分支 `dev/takeover` 收窄后的范围。`.42cog/intent.md` 已于 2026-11-12 同步到同一范围，那里只列八条的标题；门槛、清单和分级以本文件为准。
> 本文件只写「到什么程度算交付」。当前离每一条还差多少，以命令输出为准，记在 `state/takeover.md`。

## 范围

交付物是三个 Rust 入口，对外行为与固定基线 `OpenBMB/PilotDeck@cc7c4e6` 一致：

- `pilotdeck server`：gateway 的 WS 协议、HTTP 路由、鉴权、落盘格式、发给模型 provider 的请求。
- `pilotdeck` 的 CLI 子命令：参数、输出、退出码、落盘。
- `pilotdeck-agent-loop-sidecar`：独立可执行文件，stdio 与 TCP 两种部署。

不在范围：阶段 B（`ui/server`）、前端、StaffDeck、各渠道的生产实现（渠道只要求启动表现与基线一致）、Rust 原生扩展接口、按页渲染 PDF、写后语法诊断。2026-11-13 起另加六项（人答复「您来决策就好」，主会话定，理由见 `state/takeover.md`「人已定」第 13 条）：`pilotdeck tui`、`gateway setup` 的联网三步、`update` 的 Git Web 更新、遥测上报、公共 host 的 PDF 抽文本、sidecar 加载用户的 JS 模块（`PILOTDECK_AGENT_LOOP_FACTORY`）。原版 `ui/server` 接 Rust gateway 的兼容性在范围内。

## 三个口径

单看「多少个场景一致」不够：场景是实现者写的，分母可以被写小。交付时三个口径都要满足。

| 口径 | 回答的问题 | 怎么量 |
|---|---|---|
| 场景一致率 | 测到的地方对不对 | `node scripts/bbx/check.mjs`：同一场景先后喂给基线和 Rust，比较 WS 帧、HTTP、CLI 输出、发给假 provider 的请求、落盘文件 |
| 表面覆盖率 | 该测的测到没有 | `node scripts/bbx/coverage.mjs --surface`：分母从基线源码枚举（method、参数、配置键、环境变量、事件、落盘记录、CLI、hooks 等），不由写场景的人决定 |
| 盲审收敛 | 前两个口径之外还漏多少 | 派一个不是实现者的审查者，只看基线源码和场景、不看 Rust 实现，去找差异 |

## 八条标准

全部满足才算交付。每一条的结论要有当次的命令输出或记录作证，不引用以前的结果。

### 1. 全量对拍稳定一致

- 安静的机器上（没有别的构建、测试、对拍在跑），全量对拍连续 3 轮结果完全相同。macOS 和 Linux 各做一套。
- 每轮里不一致的场景只能来自下面「允许不一致的清单」。`INVALID`、`RUN FAILED` 一律算没过。
- 每个场景的基线自比（`--self`）稳定；`volatile` 只声明基线自己也不稳的最窄路径，并写明依据。
- 场景里登记了 `accepted` 的基线 bug（Rust 有意不照做），登记范围以外的字段照常比较，登记后一致即算一致。每条登记在 `state/takeover.md`「需要人过目的决定」里有一行。
- 需要占用 18789 端口的场景只在没有真实 PilotDeck 的机器上计入（目前是 cb8）；其他机器上跳过并在结果里计数，不算一致。

### 2. 表面覆盖完整

- 表面清单里每个在范围内的项，都被至少一个结果为一致的场景碰到：「没碰到」和「只被有差异的场景碰到」两栏在范围内为 0。
- 不在范围的项逐项列出理由，汇总成一张表由人过目。没有理由的不算不在范围。

### 3. 盲审收敛

- 连续两次盲审，各自覆盖全部在范围内的区域，都找不出第 1、2 级的新差异（分级见下）。
- 盲审者不能是该区域的实现者，设计场景时不读 Rust 实现。每次盲审记下：谁审的、覆盖了哪些区域、找出什么、各是几级。

### 4. 原版界面可用

- 原版 `ui/server` 加前端接 Rust gateway：`scripts/ui-smoke` 通过。
- 人亲手用一次：对话与工具、权限询问、会话续写与历史。

### 5. 构建与测试全绿，没有占位

- 四条命令（`cargo fmt --all --check`、`cargo clippy --all-targets -- -D warnings`、全量 `nextest`、文档测试）在 Linux 上全部通过：接手仓库的 CI 和 cb8 各一次。macOS 上已知的环境性失败逐个列明原因。
- 范围内没有 `unimplemented!`、`todo!`、`NOT_IMPLEMENTED`、空的 match 分支、转发给 TS 的兜底；grep 出来的每一处逐条说明。

### 6. TS gateway 退役

- 透明代理模式已删除，`pilotdeck-gateway` 没有转发给 TS 上游的路径。
- 全量对拍和界面冒烟期间，Rust 一侧的进程树里没有 Node 的 gateway 进程，留有进程列表作证。
- 独立的 sidecar 可执行文件保留。

### 7. 性能报告

- 发布构建，同一台机器，基线与 Rust 各量一遍：启动到开始监听的耗时、每轮开销（假 provider 下）、空闲与若干轮之后的内存、并发会话。
- 报告写明机器、构建方式、每项重复次数和波动。这一条要求的是数字，不设通过门槛；比基线差的项列为问题并定级。

### 8. 真实使用

- 人在最终组合上完成一组真实任务：界面上的对话与工具、交互与恢复、历史数据；CLI 的常用命令。
- 主会话准备隔离的候选环境、步骤清单和证据；没做的如实记为待验。

## 问题分级

每轮验收发现的问题记入台账，按级别排处理顺序。这是工作方法，不是第九条标准；它与标准的关系是：第 1、2 级在交付时必须为零（否则第 1、3 条过不了），第 3、4 级要么修掉、要么列明并经人过目。

| 级 | 是什么 | 例子 |
|---|---|---|
| 1 安全与数据 | 权限、沙箱、路径检查的差异；会话文件丢失或损坏；崩溃、挂起 | 安全相关的配置在 Rust 里不生效 |
| 2 主路径 | 界面和 CLI 实际用到的 method、发给模型的请求、落盘格式 | 某种协议的请求头或请求体与基线不同 |
| 3 边角 | 少见参数、错误文案、少用的配置键 | 非字符串参数的处理 |
| 4 时序与外观 | 帧的先后、日志行 | 两条通知的次序偶尔相反 |

另有一类单列、优先处理：**尺子本身的问题**——对拍场景在并行或负载下偶发不一致、基线自比不稳、采集器的平台假设。它们不是产品缺陷，但让第 1 条的数字不可信。

基线自身的 bug（崩溃、挂起、丢数据；与它自己的类型、文档或测试矛盾；安全问题）Rust 不照做，登记为已接受差异，不占上面的级别。其余「看着像缺陷」的基线行为照基线做。
